## The claim audit

The sweep's largest class of finding was not a defect in the code but a
**claim in the documentation that the code does not support**. Nine
documentation rows were wrong and are now corrected (BUGS.md RT-45 to
RT-50): the gateway adapter descriptions (the webhook is not a "stub",
WhatsApp/Email/SMS are not "config-only"), the error-class and hook-event
counts, the CLI command count, the overlay count, the crate tree, the
TUI "bridge", and two CLI stubs described with invocations that do not
exist.

One false correction was made and reverted: iter-1000 removed "and server"
from the README's MCP row on a search that covered
`operant-core/src/mcp.rs` only, and missed
`crates/operant-cli/src/mcp_serve.rs` — 955 lines implementing an MCP
SERVER over stdio. The original row was right.

**The rule this suggests:** a claim in a document is worth exactly what the
search behind it covered. A count is not a fact until it has been derived
from the code, and a "this does not exist" finding needs the WHOLE
workspace searched, not one file.

### Genome reconciliation — iter-1056

The four workflow boards under `docs/kb/workflows/` were stale, and stale in
the direction that costs the most: they listed as **open** work that
`docs/audit/2026-06-19-BUGS.md` had already recorded as **fixed**. 39 board
rows described defects that were closed between iter-958 and iter-973. An
agent reading a board to pick up work would have re-opened, re-diagnosed and
re-fixed findings that are already fixed — and the boards are the collision
guard, so a fresh claim on one of those rows would have looked legitimate.

The rule this exposes: **a board's status is a claim, and `docs/audit/2026-06-19-BUGS.md`
is the owner of the fix state.** The board was written when the sweep found the
defects; nothing ever walked back to mark the rows. `genome doctor` did not
catch it, because the boards were internally consistent — open rows with a
valid id are exactly what the schema expects. It is now RG-001, the first
record in a regressions ledger that was empty while the sweep was producing
exactly this class of lesson.

All four boards are now reconciled (0 open): `holon-seat-redteam` (17 rows),
`tui-redteam` (12), `knowledge-base-redteam` (20 findings plus the reachability
and next-work notes), and `org-tui-foundation` (3). Each row names the fixing

Per AGENTS.md this is a **cosmetic defect, not an incident**: history is

**Do not read a stale number here.** The peer is pushing every few minutes, so
any "next free label" written in a document is false by the time it is read —
this note said iter-1057 and both iter-1057 and iter-1058 were then taken twice.
Re-read the authority before every push:

```bash
git fetch origin
git log origin/main --oneline | rg -o 'iter-[0-9]+' | head -1   # top label, then +1
```

The duplicates are also systemic rather than new: roughly 200 labels are
duplicated somewhere in `origin/main`'s history and 715 commits carry no label
at all (the genome tool's own commits are among them), so a collision is the
normal failure mode of the read-then-write race the fork protocol names, not a
sign that this session went wrong. The next free label is computed at commit
time, never copied from a document.
