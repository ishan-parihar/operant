`crates/operant-cli/src/mcp_serve.rs` — 955 lines implementing an MCP

workspace searched, not one file.

`iter-1056` is held by two commits (`b03b3970` docs, the genome
reconciliation; `2cd0451d` fix, the Slack and Discord adapters), and `iter-1057`

Per AGENTS.md this is a **cosmetic defect, not an incident**: history is
append-only, both commits stand, and no renumbering is done.

**Do not read a stale number here.** The peer is pushing every few minutes, so
any "next free label" written in a document is false by the time it is read —
this note said iter-1057 and both iter-1057 and iter-1058 were then taken twice.
Re-read the authority before every push:

```bash
git fetch origin
git log origin/main --oneline | rg -o 'iter-[0-9]+' | head -1   # top label, then +1
```

The duplicates are also systemic rather than new: a few hundred labels are
duplicated somewhere in `origin/main`'s history and a comparable number of
commits carry no label at all (the genome tool's own commits are among them),
so a collision is the normal failure mode of the read-then-write race the fork
protocol names, not a sign that this session went wrong. Derive both if you
need them:
`git log origin/main --oneline | rg -o 'iter-[0-9]+' | sort | uniq -c | awk '$1>1' | wc -l`
and `git log origin/main --oneline | rg -v 'iter-[0-9]+' | wc -l`. The next free
label is computed at commit time, never copied from a document.
