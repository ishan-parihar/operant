## 2. Critical Findings

### F1 — Memory provider is NEVER attached to the agent in CLI/TUI (`🔴 High`)

`operant-cli/src/main.rs`:
- `create_runtime_agent()` / `create_agent_without_events()` call `.with_memory_manager(...)` and `.with_skill_manager(...)` — **never `.with_memory_provider(...)`**.
- `load_memory_manager()` builds the provider via `build_memory_provider(...)` and calls `provider.initialize("main")` in a fire-and-forget task, then **drops the Arc**. The provider object is discarded.
- The TUI (`adapter_types/tui_app.rs:449,814`) also goes through `create_runtime_agent` — same gap.
- **Consequence:** every agent-side memory hook is dead code in the interactive paths: `sync_turn` after each turn, `prefetch` (agent-side recall injection), `on_session_end`, `on_pre_compress`, `on_memory_write` mirroring, `on_delegation` observations. Only the gateway (`gateway_runner.rs`) wires a provider manually at the handler level (prefetch + sync_turn per message).
- `with_memory_provider` has exactly **one call site** in the whole workspace: its own definition (`agent/mod.rs:428`).

### F2 — Two parallel memory systems that never talk (`🔴 High`)

1. **`operant-core::memory_provider`** — trait + `TdgMemoryProvider`/`BuiltinProvider` (MEMORY.md/USER.md). Wired to gateway only.
2. **`operant-memory` crate** — a full semantic memory stack (SQLite/Markdown/Lucid/Qdrant/Postgres backends, embeddings, hybrid retrieval, consolidation, decay, knowledge graph, snapshot/hydrate, response cache). Used heavily by `operant-runtime` agent (`loop_.rs`, `agent.rs`), `operant-gateway`, `operant-channels` orchestrator, cron, daemon, SOP, and the memory tools (`memory_store/recall/forget/purge/export`).

The two never exchange data. A memory written via the runtime loop's `create_memory(...)` is invisible to the core agent's provider, and vice versa. This is the single largest architectural debt.

### F3 — Memory context is not injected into the agent's system prompt in CLI/TUI (`🟡 Medium`)

- `build_frozen_prefix()` = system prompt + skills only. `MemoryProvider::system_prompt_block()` and `prefetch()` results are never injected into the turn request in the interactive path (the gateway prepends `[retrieved_memory]` to the query manually — the agent itself does not).
- `MemoryManager::build_memory_context(2000)` exists but is only reachable via `BuiltinProvider::prefetch` — which never runs (see F1).

### F4 — TDG-specific bugs (removal targets — moot once F1 is fixed, but documented for the record) (`🟡 Medium`)

- **Three divergent search paths**: `prefetch` uses `HybridRetriever` (FTS5+trust+recency), `tdg_search` tool uses FTS5, `handle_tool_call("tdg_search")` uses `LIKE %query%` sequential scan.
- **Invalid `developmental_stage: Some(0)`** in `memory_provider.rs::handle_tool_call`'s `tdg_create` (Stage enum is 1–8) — the standalone `tdg_tools.rs` was fixed to `Some(1)`, the provider path was not.
- **Duplicate/conflicting tdg tools**: `register_tdg_tools` registers `tdg_connect` (arg `relation`+`strength`) while `TdgMemoryProvider::tool_schemas()` advertises `tdg_connect` (arg `edge_type`) — if both were ever wired, the agent would see two schemas for one tool with different arg names.
- `tdg-rust` is an **external sibling path dependency** (`../../tdg-rust`) outside this repo — the build is not self-contained.
- Silent downgrade: `provider = "tdg"` with the feature off silently falls back to `builtin` with no user-visible warning.

### F5 — Browser providers are fetch-only (`🟡 Medium`)

- `LightpandaProvider` / `ObscuraProvider` implement only `navigate` (markdown dump via `fetch --dump markdown`); `click`/`type_text`/`scroll` return hard errors.
- `ObscuraProvider` downloads from `h4ckf0r0day/obscura` releases — unverified third-party repo, no checksum verification, and the tar.gz is never extracted (download writes the archive to `~/.operant/bin/obscura` and then runs it).
- No browser session persistence, no JS evaluation, no vision, no console capture.

### F6 — Web tooling gaps (`🟡 Medium`)

- `web_fetch` returns the **raw body** (HTML) — no markdown extraction, no JS rendering. There is **no `web_scrape` and no `web_extract` tool** in the core registry (grep: `web_scrape` only appears in gateway emoji tables).
- `web_search` default is DuckDuckGo Lite HTML scraping — fragile markup parser.
- `tools.igs_enabled` config flag exists but **no igs implementation exists** anywhere.

### F7 — Known parity gaps vs hermes-agent (from `docs/HERMES_VS_OPERANT_AUDIT.md`)

- Prompt caching (Anthropic `cache_control` injection) — missing.
- Streaming context scrubber — missing.
- Skill scaffolding stripping — missing.

## 3. Contrast with hermes-agent-ultra

`hermes-agent-ultra` (Rust, 24 crates) is the reference architecture this project is ported from. Relevant differences:

- **`hermes-tool-planning`** — dedicated tool-planning crate (multi-step tool orchestration). Operant has `operant-tool-call-parser` (parsing) but no planning layer.
- **`hermes-intelligence`** — web intelligence gathering. Operant's `web_tools.rs` is a thin DDG/Tavily/Exa wrapper. **This is the crate igs-rust replaces/upgrades.**
- **`hermes-provider-runtime` / `hermes-app-runtime`** — provider lifecycle + app runtime separation. Operant keeps all of this in `operant-runtime`.
- Both share the hermes lineage (the operant codebase explicitly ports hermes-agent patterns — `MemorySyncExecutor`, `IterationBudget`, `TurnDiagnostics`, etc.).

**Net:** operant's loop is at parity or ahead on resilience (rotation, compression, interrupt), but lags on *intelligence/tooling breadth* (web, browser) and *memory cohesion* (F2).

## 4. Decisions (user-approved, 2026-08-02)

| Decision | Choice |
|----------|--------|
| Replace TDG memory | Remove `tdg` feature + `tdg-rust` dep + `TdgMemoryProvider` + `tdg_tools.rs` entirely |
| agentmemory integration | **REST client + MCP**: new `AgentMemoryProvider` implements `MemoryProvider` via HTTP to `localhost:3111`; agentmemory MCP stdio server (`npx -y @agentmemory/mcp`) registered in `McpManager` for the 53 tools |
| agentmemory server management | **Auto-spawn**: operant runs `npx -y @agentmemory/agentmemory` when the health endpoint is unreachable; shuts down on exit |
| igs-rust integration | **CLI subprocess** (`igs web scrape --url … --format json`, `igs browser …`) for browser/web-extract/web-scrape |
| Defaults | `memory.provider = "agentmemory"`; `browser.provider = "igs"`; `tools.igs_enabled = true` |

### Post-review fixes applied (code-reviewer findings)
- `web_search_igs` was dead code AND used a wrong flag (`--limit` vs the CLI's `--max-results`). Now `IgsSearchProvider` (structured JSON parse + defensive shape handling) and wired into `WebSearchTool`; falls back to DuckDuckGo when igs returns zero results (its Tavily/Firecrawl upstream needs a key). `preferred_provider` default = `"igs"`.
- Verified `igs browser` is a persistent session (goto → markdown → click across calls) ✓.
- Verified gateway builds its agent via `create_runtime_agent` (provider attached) ✓.
- Verified auto-spawn uses `npx -y`, tracks the child, `kill_on_drop(true)`, warmup polls health 1s×60 ✓.
- Memory tests use unreachable `:1` port — deterministic ✓.

### Known intentional design points
- Builtin `MemoryManager` (MEMORY.md) and agentmemory run side-by-side: file-backed memory remains the lightweight fallback; agentmemory is the semantic backend. Both inject into the volatile suffix; prefetch is capped at 5 results / 2048-char context.
