Status: **audit + implementation plan.** The plan's work packages W1–W8 (§5) are the next
iterations. Holon's side of the same audit (kernel bugs, the local installation, the legacy
kernel gaps, and the cross-repo wave order) is in Holon's personal overlay,
`holon-personal/docs/design/2026-10-15-integration-install-kernel-audit.md`.

Scope: everything `docs/agentic-os/` says landed, audited at `origin/main` 4d9b9adb
(iter-822 … iter-836), against `BOUNDARY.md`, `ORG-LAYER-DISPOSITION.md`,
`IMPLEMENTATION-PLAN.md` and Holon's `docs/CONTRACT.md` §1, §8–§12 (Holon `c20d63d`).

Method:

- each command operant sends to `holon` checked against Holon's argparse definitions;
- `cargo test -p operant-os` run in a clean worktree: 13/13 pass, but the 5 read-API tests skip

## 1. Verdict

The code for phases B–H exists and is unit-tested, but **in a real Holon run almost none of it
switches on.** The kernel exports `HOLON_BRIEF_DIR` and `HOLON_EMPLOYEE_ID`. Operant keys on
`HOLON_RUN_DIR` and `HOLON_EMPLOYEE`, which nobody sets (O-01). So in a real run:
- policy enforcement never mounts;
- `trajectory.json` and usage are never written;
- the cron tool's org-mode gate never fires.

The native Holon tools are not registered for Holon bodies (O-03), and two of them call the
kernel with arguments it rejects (O-04). Phase F's Chair channel and event intake are library
code that nothing calls (O-14, O-15).

Four findings are security issues that must be closed before org mode is turned on anywhere:
- the supervisor passes its whole environment to agent bodies (O-07);
- the Notion webhook arm drops the secret path that protected the token rotation (O-08);
- untrusted channel text can name a file the kernel reads (O-09);
- the observe posture permits mutating HTTP (O-10).

Live state: `~/.operant/operant.toml` has no `[holon]` section, so the workstation gateway runs
in personal mode. The org stores are not archived. Its 10 enabled cron jobs still run. The live
Holon instance (`~/holon`) has never run an operant-bodied stage. None of the integration has
been exercised on live data. That is why these defects are latent rather than incidents.

## 3. Findings

Severity: **P0** means the integration does not function, or there is a security hole. **P1**
means a plan acceptance is unmet or a correctness bug. **P2** covers quality, tests and docs.
Line numbers are at `origin/main` 4d9b9adb.

### P0: the integration does not engage

**O-01: the run-env contract is misnamed.**
- Operant reads `HOLON_RUN_DIR` in:
  - `operant-cli/src/main.rs:2411` (trajectory recording);
  - `operant-core/src/agent/prompting.rs:113` (trajectory.json, usage);
  - `operant-core/src/tools/cron_tool.rs:86` (org-mode cron gate);
  - `operant-os/src/enforcement.rs:39` (policy mount).
- Holon exports `HOLON_BRIEF_DIR` (CONTRACT §1; `holon/execution/drivers.py:156`), which is the
  same directory.
- Verified live: a body run by `operant org holon supervise` had `HOLON_BRIEF_DIR` and no
  `HOLON_RUN_DIR`.
- Why the tests missed it: `tests/enforcement.rs` builds the authority directly from a policy
  file and never goes through `run_policy()`'s env read.
- Fix:
  - read `HOLON_RUN_DIR`, falling back to `HOLON_BRIEF_DIR`, in one helper in `operant-os`
    (`run_dir()`), used by all four sites;
  - Holon adds `HOLON_RUN_DIR` to its run env and CONTRACT §1 (Holon H-01).
- Accept: an integration test runs `operant run` under the env a real
  `holon dispatch --prepare --json` returns, with a scripted provider. It asserts:
  - the "policy.json enforcement mounted" log line;
  - `trajectory.json` beside the brief;
  - `usage` in `result.json`.

**O-02: the seat id comes from the wrong variable.**
- `enforcement.rs:29` reads `HOLON_EMPLOYEE`. The kernel exports `HOLON_EMPLOYEE_ID`, which
  `tools.rs:90` already uses.
- The fallback to the run id keeps the consult self-consistent. But escalations, logs and any
  later per-employee state are keyed on a run id, not the employee.
- Fix with O-01: one `holon_employee()` helper.

**O-03: native tools are never registered for Holon bodies.**
- Registration is gated on `config.holon.enabled` (`main.rs:1029`).
- A Holon body runs with the adapter's posture configs (`observe.toml`, `act.toml`), which have
  no `[holon]` section. So the tools are absent.
- The adapter still mounts the Python `holon mcp` server per run (Holon
  `adapters/operant/install.py:117`). iter-830's "the resident holon mcp retires" is not true of
  any real run.
- Fix:
  - register when the *run env* says this is a Holon run (`HOLON_RUN_TOKEN` and `HOLON_HOME`
    set), independent of config, matching how each tool's `is_available` already gates;
  - then the adapter drops `[[mcp.servers]] holon` for operant builds that carry the tools
    (Holon side, version-gated).
- Accept: an operant body's tool list contains the `holon_*` native tools and no `holon` MCP
  server, and no Python process stays alive during the run (phase E's acceptance).

**O-04: the native tools call the kernel with arguments it rejects.**
- `holon_memory_add` runs `holon memory add <text>` (`tools.rs:232`). The kernel requires
  `--scope`, `--kind` and `--content` (Holon `cli.py` "memory add"). It fails on every call.
- `holon_submit` runs `holon --json submit <run> <json>` (`tools.rs:337`). `submit` takes
  `run_id` and `--file`, with no positional envelope. It fails on every call, and this is the
  tool observe stages need to hand in a result.
- `holon_msg_send` describes `to` as "employee id" (`tools.rs:283`). The kernel wants
  `emp:<id> | dept:<slug> | org | chair`.
- The kernel binary is `$HOLON_BIN`, else `holon` on `PATH` (`tools.rs:33`, `run.rs:46`).
  - The contract exports `HOLON`: a shell command string such as
    `/usr/bin/python3 -m holon --home …`.
  - On this workstation `holon` is on no `PATH` (`~/bin` is not on `PATH`), so every CLI-backed
    tool fails with ENOENT.
- Coverage: 7 tools against the 23 of `holon mcp` (`AGENT_COMMANDS` in `holon/mcp.py`). Missing:
  - `msg inbox`: an employee cannot read replies;
  - `msg request`: cross-department work;
  - `task show`, `task tree`, `plan show`;
  - `memory context`;
  - `skill list`, `skill show`, `skill invoke`: playbooks;
  - `run show`, `run heartbeat`;
  - `metrics`, `classify`, `routine list`, `dept roles`.
- Fix:
  - generate the native tool set from one definition, so the two cannot drift (S2). Either
    ship the kernel's tool list as a vendored JSON file (`holon mcp --list-tools --json`) and
    build tools from it, or port each command with its exact argv;
  - pass free text by stdin (O-09);
  - resolve the kernel through `$HOLON` (`sh -c`-free: split once with `shlex` rules) or a
    `[holon] bin` absolute path.
- Accept: a test drives every native tool against a scratch instance (the `HOLON_REPO`
  fixture) and asserts exit 0 and the expected row: a memory item, a message, a submitted run.

**O-05: the observe allowlist names tools that do not exist.**
- `policy.rs:73-81` allows `holon_memory_store`, `holon_msg`, `holon_work` and
  `holon_task_show`. None exists.
- The real `holon_memory_add` and `holon_msg_send` are not on the list, so an observer
  (research, plan, verify) is denied them as escalations.
- Fix: one `pub const` list of native tool names in `tools.rs`, used by `register_all` and
  `OBSERVE_ALLOW`.
- Accept: a test fails if any `holon_*` entry in `OBSERVE_ALLOW` is not registered.

**O-06: the operant body's home is a literal placeholder.** (Holon file; listed here because it
breaks every operant body.)
- Holon `adapters/operant/driver.toml:27` sets `HERMES_HOME = "{holon_home}"`.
- Driver `[env]` values are not templated, and `install.py` replaces only `{operant}` and
  `{ohome}`. Loading the installed driver gives `{'HERMES_HOME': '{holon_home}'}`.
- `operant_home()` (`operant-core/src/platform.rs:98`) then resolves the relative path
  `./{holon_home}` under the run's cwd, which is the work directory. As a result:
  - every operant body writes its sessions, org stores (`org/grants.db`, `org/requests.db`) and
    trajectories into the work directory;
  - the observe-stage working-directory fingerprint sees a new directory, a false read-only
    breach;
  - the isolation that invariant 4 relied on does not exist.
- Fix (Holon H-02): `HERMES_HOME = "{ohome}"`, replaced at install, plus a guard test that
  loads the installed driver and asserts an absolute `HERMES_HOME`.

### P0: security

**O-07: the supervisor hands its whole environment to agent bodies.**
- `supervisor.rs:37-44` spawns `sh -c` with the inherited environment and layers the prepared
  env on top.
- Holon's Python dispatcher strips `HOLON_CHAIR_KEY` and `HOLON_KEY` from what it inherits
  (`drivers.py:185`). Operant strips nothing.
- Verified live: a marker variable set in the supervisor's environment appeared in the body's
  environment.
- In the gateway, that environment carries channel tokens and provider keys. It also carries any
  `HOLON_CHAIR_KEY` an operator sets so that `run finish` can authenticate. That is a path for
  the Chair key to reach agents, which a standing rule forbids.
- Fix: `env_clear()`, then a small allowlist (`PATH`, `HOME`, `LANG`, `LC_*`, `TERM`,
  `TMPDIR`, `XDG_RUNTIME_DIR`), then the prepared env. Never pass:
  - `HOLON_CHAIR_KEY`, `HOLON_CHAIR_KEY_FILE`, `HOLON_KEY`;
  - `OPERANT_CONFIG_DIR`;
  - the supervisor's own `HERMES_HOME`.
- Accept: a unit test with a fake driver that dumps its env asserts none of those names appear.

**O-08: the Notion webhook arm drops the secret path that guarded the token rotation.**
- Holon's receiver stores any body's `verification_token` as the new `webhook_token` *before*
  any signature check (`holon_notion.py:797`, commented "Only a caller who knows the secret path
  gets this far"). The secret path is `webhook-path`, kept private by design.
- Operant mounts the arm at the fixed, guessable `/webhook/notion` (`webhook.rs:237`), with a
  default listen address of `0.0.0.0`.
- So anyone who can reach the port can:
  - replace the token, which breaks the real subscription;
  - then sign forged events with it.
- Each request also spawns an unbounded `python3`, which is a cheap denial of service.
- Fix:
  - mount the arm only at the instance's secret path (read once from `holon_notion.py
    webhook-path`);
  - bound concurrency (a semaphore of 1–2);
  - Holon H-05: `apply` never rotates the token unless the host passes `--path-verified`.
- Accept: a POST to `/webhook/notion` with a `verification_token` body is a 404, and
  `notion.json` is unchanged.

**O-09: untrusted text can name a file the kernel reads (latent until O-15 is wired).**
- Holon's text arguments read `@path` as a file and `-` as stdin, as the calling user (Holon
  `cli.py:99`).
- `events.rs:41` passes channel text as `--payload <text>`. Once wired, any Telegram user's
  message that starts with `@/home/…/model.key` and contains a trigger's pattern makes the
  gateway's `holon` read that key into the work's message. The agent sees it, and Notion mirrors
  it.
- The native tools' `memory add` and `msg send` bodies have the same shape, but run as the
  agent's user, so the risk is lower.
- Fix: never put untrusted text in argv. Pipe it on stdin (`--payload -`, `--content -`). Holon
  H-06 adds a literal form and labels event payloads as untrusted external content in briefs.

**O-10: the observe posture permits mutating HTTP and paid calls.**
- `OBSERVE_ALLOW` includes `http_request` (`policy.rs:49`). Its schema supports `POST`, `PUT`,
  `DELETE` and `PATCH` (`operant-core/src/tools/http_tool.rs:95-100`). It also includes
  `xai_http_request` and `openrouter_query`.
- The adapter's `observe.toml` does not disable them either. So an observer can change external
  systems or send outreach, and Holon's fingerprint cannot see it. This conflicts with
  "observe = change nothing" and with the pilot rule.
- Fix: observers keep GET-only fetch tools (`web_fetch`, `web_search`, `web_extract`, …).
  `http_request` is act-only, or method-restricted to `GET`/`HEAD` in observe.

**O-11: supervising an isolated instance bypasses the trust boundary.**
- With `[isolation] agent_user`, `prepare` returns an env meant for the agent user
  (`HOLON_BROKER`). Operant then runs the body as the operator, which can read the Chair key and
  `work.db`.
- Conversely, a body run correctly as the agent user cannot read `policy.json`, because Holon
  writes it `0600` as the kernel's user (`briefs.py:77`). `run_policy()` then fails closed and
  the run dies at startup.
- Fix:
  - until the Rust runner exists (O-30), `supervise` refuses an instance whose prepared env
    carries `HOLON_BROKER` (or calls Holon's runner socket);
  - Holon H-07: `policy.json` readable by the agent (group), and H-08: the prepared JSON names
    the isolation contract.

### P1: phase acceptance unmet

**O-12: the supervisor is a CLI loop, not a daemon organ.**
- Only `operant org holon supervise [--loop]` exists. `[holon] supervise`,
  `max_concurrent_runs` and `clock` are never read (`config.rs:310/318/323`). Bodies run one at
  a time.
- Defects in the loop:
  - **hot loop**: an error sets `ran = true` (`cmd_org.rs:1103`), so a persistent failure (a
    missing `holon`, a bad home) re-spawns `holon` with no sleep;
  - **heartbeat cadence** is a fixed 10 s (`supervisor.rs:52`) where the doc says lease/3. An
    execute lease is 60 min, so this is about 360 Python spawns per execute run instead of 3;
  - **timeout** kills only the `sh` (`supervisor.rs:60`; `kill_on_drop` likewise), and the
    body's process group survives;
  - **no stop-after-submit** (CONTRACT §4): a body that already handed in keeps its slot;
  - **no `driver.log`**: stdout and stderr go to the supervisor's journal, so the run directory
    lacks the evidence the Python path writes.
- Fix:
  - a gateway task (when `[holon] supervise`) with a `Semaphore(max_concurrent_runs)`;
  - one claim loop over `supervise_employees`;
  - backoff on error;
  - lease-derived cadence;
  - `setsid` and a process-group kill;
  - a run-status poll that stops the body once its result is in;
  - stdout and stderr teed to `<run dir>/driver.log`.
- Accept: the plan's phase E acceptance:
  - the Notes digest routine end to end with no Python alive during the body;
  - two concurrent bodies under `max_concurrent_runs = 2`;
  - a timeout leaves no orphan process.

**O-13: there is no clock.** No cron or no-agent job fires `holon tick`. `operant org holon tick`
is manual only.
- Fix: a gateway interval task (every 2 minutes) when `[holon] clock`, with doctor reporting the
  last tick.
- Accept: with `clock = true` and `holon-tick.timer` disabled, due routines fire.

**O-14: the Chair channel is not wired.**
- `chair::is_chair` and `run_as_chair` have no caller. Missing:
  - the gateway hook;
  - intent classification;
  - the confirmation step;
  - Holon notifications delivered to the Chair's thread.
- Fix: in the Telegram inbound path, the sender's platform user id is checked with
  `is_chair` (cached with a TTL). Then:
  - classify through `holon classify` (Holon owns `[classifier]`);
  - confirm approvals;
  - run the command;
  - reply;
  - outbound: a `[notify]` command that posts through the gateway.
- Accept: "approve <id>" from the Chair's Telegram approves a pending plan. The same text from
  anyone else is chat.

**O-15: event intake is not wired.**
- `events::match_and_fire` has no caller. There are no channel, webhook or file sources.
- It counts skipped firings as fired, because `routine fire` exits 0 on a cooldown skip (Holon
  H-13).
- Fix: call it from the gateway for each channel message and each non-Notion webhook, with stdin
  payloads (O-09) and the API connection reused. File events later.
- Accept: a webhook matching a trigger fires its routine once per cooldown.

**O-16: the Notion arm never mounts by default.**
- The fallback script path is `$HOLON_HOME/adapters/notion/holon_notion.py`
  (`gateway_runner.rs:1662`). The instance home holds `notion.json`; the script lives in the
  Holon checkout.
- `python3` is hard-coded.
- Fix:
  - derive the script from the `[holon] bin` checkout (`<bin>/../adapters/notion/…`) or require
    `notion_script`;
  - run it with the same interpreter as `bin`.

**O-17: refusals are never recorded, and escalations land in a retired store.**
- Nothing writes `result.refusals[]`.
- A headless `Escalate` is queued in `PendingRequestDb` under the operant home
  (`enforcement.rs:68`). The model is told "the next run consults the grant the approver mints".
  In org mode there is no approver and no grant.
- The disposition says org-mode escalation becomes `result.refusals[]`.
- Fix: a per-run refusal recorder (`<run dir>/refusals.jsonl`, merged into `result.json` at
  save, like usage) holding the tool, the reason and the policy rule. The org-mode message says
  "refused under policy.json; report it in your result". The in-flight G+1 rewrite of
  `seat_authority` (O-32) is the place to land it.
- Accept: plan C's acceptance. A refused call appears in `refusals`, and the Holon stage shows
  it as a blocker (needs Holon H-03).

**O-18: roots, writes and commands are not enforced.**
- `act` compiles to `Yolo` plus the deny list only (`policy.rs:146`). `roots`, `writes` and
  `commands` are parsed and unused. The doc defers paths to Holon's fingerprints.
- The plan's phase C acceptance is "a write outside `roots` is refused and never executed".
- Fix:
  - compile `roots` and `writes` into a path guard for the file tools and the AFT writers;
  - compile `commands` into the terminal allowlist (with an `act_commands` split);
  - each refusal goes through O-17.
- Accept: a `file_write` outside the roots is refused, logged, and the file is absent.

**O-19: budgets are not enforced, and usage is an estimate.**
- `PolicyBudget` is parsed (`policy.rs:99`) and never compared. `seat_budgets` is not fed from
  the policy.
- Usage is `content.len() / 4` over the final message list (`prompting.rs:175`). Input tokens are
  undercounted by roughly the number of turns, since each turn resends the context. Cost is
  always null.
- Fix: meter provider-reported usage through the `UsageAccumulator`, enforce the cap at the turn
  boundary (a budget refusal, then a clean stop), and fill `cost` when the provider prices it.
- Accept: a hard token cap ends the turn with a budget refusal, and `holon metrics` shows cost
  per verified result.

**O-20: the build is never reported.**
- `usage.build` is never set, so Holon's H10 build-regression detection is inert for operant.
- Fix: `build = "<CARGO_PKG_VERSION> (memory-wire <rev>)"`, the string `operant --version`
  prints.

**O-21: usage is lost on the submit path.**
- Usage is patched into `result.json` only when that file exists. A body that handed in through
  `holon_submit` (every observe stage) reports none.
- Fix: write `<run dir>/usage.json` always. Holon reads it when present (Holon H-04).

**O-22: learning capture (invariant 4) is not implemented.**
- In a Holon run, these still write files:
  - `skill_manage`;
  - the curator;
  - `memory_store`;
  - the background-review nudges.
- Advisor findings are not added as learnings.
- Fix: one `holon_run()` gate. Under it, these produce `skill_changes`, `learnings` and
  `proposals` annotations in the run directory (merged into `result.json`), never files.
- Accept: a Holon run leaves the operant home's `skills/` and memory store byte-identical.

**O-23: phase G gating is partial, and the routine proposal is invalid.**
- In org mode, only cast seeding and cast cron seeding are skipped. Existing cron rows keep
  running (10 enabled on the workstation). These are not gated:
  - worklog, notices, decisions writes;
  - socialization, synthesis;
  - kanban for org work.

  So "an org-mode day leaves no new row in any archived table" fails.
- The proposal printed by `operant cron add` (`cmd_cron.rs:138`) and the cron tool
  (`cron_tool.rs:95`) is `holon routine add --name … --cron … --command …`. Holon's
  `routine add` takes a positional title plus `--intent` and `--dept` (both required), has no
  `--name` or `--recurring`, and is Chair-only, so an agent cannot run it.
- Fix:
  - gate every RETIRE write path on `holon.enabled`;
  - disable the cast cron rows once their routines are approved (list them in doctor until
    then);
  - print `holon routine add "<title>" --intent "<prompt>" --dept <slug> --cron "<5-field>"`;
  - for an agent, say "propose it in your result's `proposals`".
- Accept: the plan's G acceptance, measured by row counts before and after a day.

**O-24: the archive is not consistent or complete.**
- `fs::copy` of live SQLite files (`archive.rs:78`):
  - `database.db` and `operant_cron.db` are in WAL mode, with a 5.2 MB and a 3.9 MB `-wal` now.
    The copies miss committed pages;
  - the digest is computed separately from the copy.
- Not archived:
  - `~/.operant/org/` (the cast's charter files: non-regenerable);
  - the per-board kanban files the kanban manager can create (`operant_kanban_<board>.db`; none
    on the workstation today). Glob them, don't list them.
- Fix:
  - SQLite's online backup (`rusqlite` `backup` feature) or `VACUUM INTO`, then digest the copy;
  - include the `org/` tree;
  - list what was archived.
- Accept: `sqlite3 <copy> 'pragma integrity_check'` is ok, and row counts match the source at
  the snapshot.

**O-25: doctor knows nothing about org mode.**
- The plan's B acceptance is "an api_version mismatch disables org mode with one clear doctor
  line".
- Fix: `operant doctor` checks, when `[holon] enabled`:
  - home and work.db present, and `api_version` known;
  - `bin` resolvable;
  - `supervise` with employees;
  - the notion script;
  - clock and last tick;
  - archive taken;
  - cast crons still enabled.

### P2: config, tests, docs

**O-26: config.**
